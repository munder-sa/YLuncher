# 歌詞ON時の描画負荷軽減 設計

2026-11-05。利用者の依頼は計画の作成。本書と[実施計画](../plans/2026-11-05-lyrics-render-cost.md)を作成し、実装・ビルド・実機操作には着手しない。

## 1. 目的と根拠

見た目と同期を維持したまま、単語同期歌詞の描画に使うCPU時間と合成処理を減らす。対象版は2.3.0 / 47、実装タグf0e5c9d、分析記録コミットd268acb。[実測](../../performance/2026-11-05-bottlenecks.md)ではLemonのCPUが歌詞ONで34.35〜35.90%、OFFで3.99〜4.01%（1コア100%）。CPUサンプルのRenderThread比率は70.85%、DrawFramesのp90は25.83msだった。

これは描画系を優先する根拠であって、背景、単語マスク、領域全体マスクの個別の負担は未分離。各候補を別々に実装・測定し、効果のある変更だけを組み合わせる。ON/OFF差の約9割をそのまま削減目標にはしない。

設計上の第一段階目標は、**同じ単語歌詞区間のアプリCPU中央値を基準版から20%以上減らし、RenderThread時間も短縮すること**。以前の約35%なら約28%が目安だが、正式な比較値は同条件の再測定で固定する。予測・達成保証ではなく、途中で値を動かして合格扱いにしない。

利用予定は利用者報告の1920×1080・60Hz。現在の通常画面は30Hzで、60Hzと報告するscrcpy仮想画面でも約53msの描画間隔だった。CPU軽減と60fps到達を別の評価項目にする。車載の実表示周期は未確認のまま明記する。

## 2. 維持するもの・対象外

- 22sp/Bold、左寄せ、最大2行、省略、16dp間隔、既存フォント処理と文字レイアウト。
- 800msの行送り、500msの明暗/縮小、最大100msの時間差、非現在行の0.97倍、現在の透明度と左中央の拡大縮小基点。
- 単語境界の幅24dp（境界の左右12dp）、折り返し後の未塗り行の消去、上下32dpのフェード、旧現在行の500msの塗り残し。
- 前奏/間奏の3点と点灯時刻、停止・再開・シーク・曲替え・途中の再目標化。前奏終了の既存条件も維持。
- 最大3色のジャケット背景、その色抽出/共有/失効とコントラスト4.5:1以上。タッチ範囲、120dp境界、Plain/Loading/取得失敗時の表示とsemantics。
- 可視窓方式、行の保持寿命、draw/layer段階でのアニメーション読取。毎フレームの再構成/再計測/再配置を増やさず、measure/layoutからsnapshot stateへ書かない。
- **FPS上限の引下げ、単語塗り/フェードの削除、色の簡略化は行わない。** 試験の期待値・許容誤差も弱めない。
- MediaWatcher、非表示全般の購読、利用履歴集計、通信、トークン保持、分割起動制御、SDK/Compose更新、新規依存は今回の実装範囲外。

## 4. 候補A: 点灯数が同じ間の再描画を抑える

最初の小さな実装。`InterludeDots`が直接再生位置を読む構造を、点灯個数（Int）の変化を読む構造へ分離する。初期案は既存positionを入力とする`derivedStateOf`相当の状態で、点灯個数が変わった時だけCanvasを無効化する。

- 前奏/間奏、単語の塗り進行、行送り、明暗の時計を混同しない。初回は既存のフレーム時計と点灯計算を維持し、表示の無効化を抑える。境界までsleepする新しいスケジューラーは同時導入しない。
- 現在でない点の行は保持済み点灯数とフェード値だけを描画し、共有positionの変化を描画依存にしない。
- 点灯数が同じでも、emphasis、行移動、サイズ変更等による必要な描画は止めない。
- 初期値、境界直前/一致/直後、短い間奏、期間0、停止/シーク、旧行フェードを検証。既存`interludeLitDots`の結果とTTMLの塗りモデルは変更しない。
- 点灯数不変・emphasis不変の間は点のdraw回数が増えないことを追加検証する。単語区間のframe更新は既存通り動くことを確認する。

主な効果は前奏/間奏に限られる。これだけをもって単語を歌っている区間の34〜36%が減ったとは報告しない。時計処理が残ることも明記する。

## 5. 候補B: 静止背景だけを描画層へ分離する

HomeMiniPlayerの背景を、文字/歌詞/操作部と別の背面要素へ分ける。色、位置、サイズ、角丸クリップ、padding前のグラデーション座標を現状と一致させる。背景の層にはposition/fill/indexを渡さない。

既存の描画命令を保持する層と、必要なら背景だけをOffscreenへ保持する案を順に比較する。**プレイヤー全体をOffscreen化しない**。単一の線形グラデーションを直接描く方が速い可能性もあるため、層を足したこと自体を改善の根拠にしない。

- 失効は背景色、寸法、density、クリップ条件の変更。曲だけ変わって色が同じ場合やシークだけの場合に不要な再生成をしない。
- 全画面・全曲・複数曲のBitmapキャッシュは作らない。保持対象は表示中プレイヤー背景の実寸1枚/表示だけ。
- 追加ラスタ領域の設計上限は、同時表示分の合計で8MiB相当（幅×高さ×4bytes）。上限を越える場合は現行の直接描画へ戻す。実際のGPU割当/PSSがこの計算と同一とは扱わず別測定する。
- 非表示/破棄/サイズ変更で古い層が保持され続けないことを確認。持続的なメモリ増加やRenderThreadの悪化があれば不採用。
- 主要対象はHomeMiniPlayerだけ。共有ArtworkBackgroundの色抽出や他のMediaCardの描画は必要なく変更しない。

## 6. 候補C: 単語用の重ね描画を軽くする（成立確認後に採用）

候補Bを評価した後、単語用Offscreen内部の「文字全体を描く→消す」という処理を、**塗られた部分の透明度を持つ白い文字を直接描く**方式と比較する。基底のTextと行移動、歌詞領域全体のOffscreenは維持する。

初期の実験候補は既存Androidの`RuntimeShader`とComposeの`ShaderBrush`。マスクを文字描画のBrushへ適用できるかを、小さい人工文字の比較で先に確認する。新規ライブラリ/別の描画エンジン/全画面RenderEffectは追加しない。この方式の採用は未確定。

マスクの契約は現行に合わせる。fill≤0は全透明、fill≥文字数は全白。途中では、塗り済みの上の行は白、現在の折り返し行は境界xの左右12dpで白→透明の線形変化、その下の行は透明。返す色はpremultiplied alphaの白とし、旧現在行のemphasisは既存の合成順を維持する。

- x/top/bottomは現在と同じTextLayoutResultから取得。文字幅を縮めて折り返しを変える方法は採らない。
- Shaderは毎フレーム生成/コンパイルしない。uniform等の更新はdraw段階に限定し、再構成/再レイアウトを起こさない。可視/フェード中の行の寿命で所有し、異なる行/画面で可変状態を共有しない。
- まずDrawScope上のマスクと全文字レイアウトの双方で旧方式と比較。RTL混在、結合文字、絵文字、文字の重なり、ellipsis、2行目境界、複数旧行のフェードを含む。
- `Auto`や`ModulateAlpha`へ置換するだけの変更は採らない。必要な分離まで消すと合成結果が変わる。GPUで差分が残る文字やフェードについては、旧方式を保つか、この候補を不採用にする。閾値を緩めて通さない。
- RuntimeShader/Brushの組合せで画素一致、更新反映、Robolectricの検証、実機性能のいずれかが成立しなければ、その時点の結果を残す。別方式や領域全体マスクの改変へ自動的に作業を広げない。

## 7. 評価方法と採用条件

1. 通常画面1920×1080/238dpiを主要A/B条件とし、開始前にdisplay/Activityの配置を確認する。仮想画面の追加ホームを含め、描画中のホームを1つに揃える。scrcpyの設定・音声転送、他アプリ、端末温度条件を揃え、30Hzと仮想60Hzの値を混ぜない。
2. 単語が動く同じLemonの30秒区間を基準とし、開始/終了の曲ID・位置・更新時刻・speed・playing・端末時計を保存する。候補Aには前奏/間奏の区間を別枠で用意。別曲で反復確認する際は別の表にする。
3. 各有力候補は基準/候補の30秒を3組、交互の順で計測。これを事前に定めた反復数とし、同じ単体テストの無意味な再実行とは区別する。BUFFERING、曲替え、前面変更、操作混入は除外理由を残す。基準条件を復元できなければ比較不成立とする。
4. CPUはproc差分、RenderThread/doFrameはatrace、描画数/遅延はgfxinfo、メモリはPSS/Graphicsを記録。重いトレースや転送はCPU比較窓と別にする。CPU/秒だけでなく単語区間のCPU/描画回数・描画間隔も確認し、描画頻度の低下で軽く見せない。
5. 第1段階の候補採用は、想定した区間の主要指標が3組とも改善方向で、中央値の差が基準3回のばらつき（最大−最小）を上回ることを目安にする。差が埋もれる候補は保留。全体目標20%の達成とは分ける。
6. GPU時間、doFrame、単語区間の描画間隔、deadline missed率、停止時/歌詞OFF、PSS/Graphicsに基準のばらつきを越える悪化があれば原因確認。背景キャッシュの固定メモリ増分だけは§5の予算内で別記し、CPU効果と合わせて採否をレビューする。継続増加は許容しない。
7. 人工歌詞/人工背景の同時刻画像で境界・文字・色・配置を検証し、現行の1/255等の許容誤差を維持する。実曲での読みやすさ、送り/塗りの見た目は利用者にも確認してもらう。実歌詞やトークンをテスト資材/Gitへ保存しない。

60fpsの最終評価には、アプリの実周期が約16.7msである環境を確認した上で、遅いフレームと提示周期を測る。表示モード60Hzだけで合格にしない。今回は端末のHz設定変更や車載接続の再現を実装へ含めない。

## 8. 決めたこと・未確定

- 計画のみを作成し、実装は既存codex-run運用で別途開始する。
- 候補A→B→Cを直列に評価する。候補Cは成立確認を先に行い、不成立なら旧方式を維持する。効果のない変更をまとめて採用しない。
- 目標20%、比較3組、背景追加ラスタ領域8MiB相当を初期の設計値として明示する。効果を見て基準を都合よく変更しない。
- 見た目、フレーム更新頻度、既存テスト、上下端のOffscreenを維持する。全体の描画エンジン置換や表示の簡略化は対象外。
- 未確定なのは背景再利用の実効性、Shaderの画素同等性/実機効果、実車60Hzでの周期。いずれも検証ゲートで判断する事項で、確認済みの実装方法として扱わない。

技術根拠: [Composeの描画キャッシュ/層](https://developer.android.com/develop/ui/compose/graphics/draw/modifiers)は描画オブジェクトの保持とラスタ化を区別している。[CompositingStrategy](https://developer.android.com/reference/kotlin/androidx/compose/ui/graphics/CompositingStrategy)は重なりに対するalpha処理の違いとマスク用Offscreenを説明している。[Brush](https://developer.android.com/develop/ui/compose/graphics/draw/brush)、[RuntimeShader](https://developer.android.com/develop/ui/views/graphics/agsl/using-agsl)は候補CのAPI候補の根拠であり、YLuncherでの同等性や性能を保証する資料ではない。
