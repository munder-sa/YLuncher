# Apple Music 歌詞取得の設計

最新状態(2026-11-04 20時台): 後続の[接続保持設計](2026-11-04-apple-token-retention-design.md)とTask 188/189の通信改善を実装したbeta6で、Lemonと怪獣のApple実TTML採用・ホーム/パネル表示、停止/シーク・OFF/ONを確認。Lemon40行/277単語、怪獣46行/318単語。利用者の同期評価等は未完了。以下は手動入力/メモリ保持だった初期設計であり、認証保持と通信依存の現在仕様は後続設計/Taskを優先する。最新検証は[Task 179](../../../tasks/179-apple-lyrics-beta.md)末尾と[引き継ぎ](../../HANDOFF.md)を参照。

2026-11-04。初期ベータでは、ユーザーが入力した Apple Music Web 用トークンを使い、再生中のカタログ曲の単語同期歌詞を取得する。取得できない場合は既存の AMLL → LRCLIB を利用する。画面と単語の塗りは既存実装を使う。

ユーザーは Task 170 の検証を基にした方式と、初期ベータの手動入力方式を了承した。以下の保持期間・通信上限・分割は司令塔の設計判断。Task 175〜178で実装と対象検証、179で2.3.0-beta1 / 41のAPK作成・実機導入・権限維持とUIの確認を完了した。利用者がトークンを入力し、Androidで地域jpの認証接続に成功。歌詞API・実歌詞のKotlin解析/表示は未確認。

## 根拠と未確認事項

- [Task 170 の検証記録](../../../tasks/170-apple-lyrics-web-probe.md): Lemon、カタログ ID `1537460612`、認証ありで単語同期・行同期とも HTTP 200。単語同期は40行、開始・終了時刻付き span 277個。認証なしでは曲情報200、歌詞404。これは過去の検証結果であり今回の再測定ではない。
- [検証スクリプト](../../../scripts/apple-lyrics-probe.py): 公開 Web 資産から Bearer を取得し、ユーザー入力の `media-user-token` と併用。`/v1/me/storefront` の結果を使って `amp-api.music.apple.com` から取得する。
- [共有会話](https://chatgpt.com/s/cx_6aeaa93b798c8191bb6725a0fcf351cb)は取得できなかった。共有会話だけにある結論を確認済みとは扱わない。
- 現行コードには `LyricsIdentity.appleMusicId`、`TtmlParser`、`LyricLine` / `LyricWord`、AMLL / LRCLIB の取得とキャッシュがある。
- 現行 `LyricsRepository` は AMLL の単語キャッシュで早期終了する。そのまま先頭に処理を足すだけでは Apple 優先にならない。
- 現行パーサーは単語同期専用。`end` は検証に使うがモデルには保存せず、重なる主旋律や入れ子の時刻付き span を採用しない。取得成功と、このパーサーでの採用成功は別に判定する。
- Task 175の追加実測で、単語同期のJSON経路 `data[].attributes.ttml`、40行・時刻付きspan277個、namespaceと時刻形式を確認した。時刻付きdivが10個あり、主旋律の時刻解釈と重なり、他曲・別地域・Androidからの取得・トークン更新は後続ベータの確認事項。詳しい構造は[Task 175の結果](../../../tasks/175-apple-lyrics-contract-probe.md)を参照。

Apple の公式 MusicKit は開発者トークンとユーザー認証の仕組みを提供するが、今回実測した Web 用トークンとの互換性や歌詞エンドポイントへの利用可否は未確認。公式 SDK の導入だけで置き換えられるとは判断しない。[MusicKit](https://developer.apple.com/musickit/)、[開発者トークン](https://developer.apple.com/documentation/applemusicapi/generating-developer-tokens)。今回の Web 取得方式は独立した取得元として分離する。

## 初期ベータの範囲

対象は `com.apple.android.music` が再生する、既存の識別処理でカタログ ID が確定した曲。数字だけであることに加え、1〜20桁・全桁ゼロではないことを Apple クライアント入口で確認する。ライブラリ専用 ID、ID 不明、キー間の矛盾、他アプリでは Apple に問い合わせず既存経路を使う。曲名から Apple の曲を検索する機能は加えない。

優先順位は **Apple の単語同期 → AMLL の単語同期 → 既存 LRCLIB**。Apple の行同期のみのデータは初期ベータの採用対象外とし、AMLL / LRCLIB に進む。Apple の行同期対応、`end` を使った休符の忠実な再現、対唱・翻訳・音訳表示は後続候補にする。

再生・一時停止・シーク・お気に入りの仕組み、ホームとパネルの描画、既存キャッシュの形式は維持する。新しい描画ライブラリ、常駐 WebView、常時ポーリングは導入しない。

## 認証と設定

設定に「Apple Music の歌詞」を追加し、接続状態、マスク入力、接続確認、解除を提供する。ユーザーが自分の Web 用トークンを入力する。Android の Apple Music 内部設定や他アプリの保存情報から取得しない。

初期ベータのトークンはメモリ内のみ。入力欄は `rememberSaveable`、設定 JSON、Bundle、クリップボードの自動読取、ログに載せない。画面を離れたら入力欄を消し、解除・プロセス終了で接続情報も失う。設定画面に「アプリの再起動後は再入力」と表示する。トークンの永続保存は日常利用段階の別設計にする。

入力の前後空白を除き、空値・改行・制御文字・UTF-8で16KiB超を拒否する。Bearer とユーザートークンを分離して管理し、接続の追加・差替え・解除ごとに秘密値を含まない世代番号を更新する。トークンを持つオブジェクトの自動 `toString` や例外へ秘密値を含めない。

接続確認は利用者の明示操作で行い、公開 Bearer の取得と `/v1/me/storefront` の確認までを行う。この操作は歌詞表示オフでも実行できるが、歌詞は取得しない。自動の取得経路では歌詞オフ・未接続なら Apple を含む通信を開始しない。

storefront は認証応答の2文字の小文字コードを検証して使い、`jp` に固定しない。接続確認が失敗したら利用可能状態にせず、既存の歌詞取得は継続する。

## 取得処理

取得処理は `AppleLyricsTransport`、`AppleWebTokenProvider`、`AppleMusicSession`、`AppleLyricsClient` に分離する案とする。既存の coroutines・JSON・HTTP/XML 処理を使い、新規依存は追加しない。クラス名と具体的な契約は各指示書で固定する。

1. 公開要求は `https://music.apple.com` のページと同ホストの JS のみ。ユーザートークンを送らない。同一ホストの公開リダイレクトは最大3回。
2. 認証付き要求は `https://amp-api.music.apple.com:443` の固定経路のみ。ユーザー入力・JSON 内の URL を取得先に使わず、リダイレクトは追わない。
3. 標準経路は `/v1/catalog/{storefront}/songs/{id}/syllable-lyrics`。Task 175 で確認した JSON 経路だけから TTML を取り出す。`include[songs]` 付き曲情報と `/lyrics` の毎曲併用は行わない。
4. 入出力・JSON/XML解析はメインスレッド外。TTML を既存 `TtmlParser` に渡し、`WordSynced` のときだけ採用する。非対応・不正なデータのために既存検証を緩めない。
5. 位置更新・ジャケット更新・同じ曲の一時停止では取得を増やさない。600ms の曲変更待ちと `collectLatest` を維持し、曲変更・歌詞オフ・解除で要求と読み取りをキャンセルする。反映前に曲・認証の世代を照合する。

設計上の上限は次のとおり。Android と実データで満たせるかはベータで計測し、不足なら根拠を残して改訂する。

| 対象 | 上限・扱い |
|---|---|
| 公開 Web 資産の初期化 | ページ/JS各8MiB、JS最大8本、合計16MiB、全体30秒。接続確認または必要な再認証時のみ |
| API 応答 | 2MiB。非200の本文は診断へ出さない |
| 抽出する TTML | UTF-8で512KiB。既存XMLの深さ・行・span・文字数制限も維持 |
| 曲ごとの Apple 試行 | 全体5秒。期限超過は既存取得元へ進む。更新を含め無制限に延長しない |
| Bearer 更新 | 有効期限前に再利用可否を判定。認証失敗時の公開資産更新は1取得サイクルで最大1回。同時更新をまとめる |
| 診断 | 取得元、固定の理由コード、HTTPコード、所要時間、行/span数だけ。本文・ヘッダー・生の例外・認証値を出さない |

401/403は「接続の再確認が必要」とし、ユーザートークンの期限切れだと断定しない。Bearer 更新後も失敗する場合は Apple の自動再試行を止め、設定の接続確認へ案内する。404は「この認証・地域・曲で取得できない」としてフォールバックし、全取得元の Missing に変換しない。429/503は有効な `Retry-After` を尊重し、無効・欠落時は60秒待機。その他のネットワーク/5xx失敗も同じ曲は最低60秒空ける。待機と再認証は既存取得元を妨げない。

## Repository とキャッシュ

既存 AMLL / LRCLIB のキャッシュをまず暫定表示してよいが、Apple 対象の曲はそれだけで処理を終了しない。Apple の結果が採用可能なら単語同期へ切り替え、失敗時は表示済みの歌詞を保持して既存処理を完了する。キャッシュのないときも Apple の5秒上限後には既存経路へ進む。

Apple の結果は LRCLIB / AMLL のディスクキャッシュに書き込まない。初期ベータは解析済み歌詞のメモリキャッシュだけを持ち、鍵を `認証世代 + storefront + Apple ID + query.cacheKey + parser版` とする。成功は30分、最大8曲・歌詞文字列のUTF-8換算合計2MiB。容量値はヒープ実測値ではない。単一結果が上限を超えたら表示だけして保持しない。解除・認証失敗・差替えで全削除する。

404/非対応の抑制は同じ鍵で60秒、通信失敗や認証失敗を恒久的な欠曲として保存しない。全ソースが失敗した場合も認証問題は歌詞状態と別に設定画面で表示する。既存 LRCLIB の10/30/60秒再試行から Apple を毎回呼び直さない。

## 実装開始と採用の条件

1. Task 175でレスポンス構造を記録し、未知の JSON 経路や TTML 形式を推測せず固定できること。
2. 偽通信・合成TTMLで失敗分類、上限、キャンセル、キャッシュと認証世代を検証すること。
3. Android のベータで実際の取得結果を既存パーサーに通し、少なくとも Lemon と別のカタログ曲で主旋律の単語同期が表示されること。件数だけで歌詞・音源の一致を判定しない。
4. ホーム/パネル、曲送り、停止/シーク、通信断、歌詞オフ、解除、再入力、プロセス再作成、他アプリで確認すること。実歌詞やトークンをテスト資産・Git・診断に保存しない。
5. 実機未確認、再認証未確認を実装完了や安定運用と同一視しない。日常利用用の保存/ログインは、このベータの結果を基に別途決める。

Apple機能の確認用は2.3.0-beta1 / 41でapp/panelhostを揃え、実機も両方同版へ導入済み。正式版への昇格は未定。版を決めた時点ではGitタグ一覧の読み取りが実行環境側に拒否されており、新しい配布履歴を照会できたとは扱わない。

## 決めたこと

- 最初は検証済みの Web 用トークンを手動入力する。自動ログイン・公式 SDK トークンとの互換性を前提にしない。
- 初期ベータはメモリ保持のみとし、日常利用向けの永続保存を後続に分ける。
- Apple 対象は Apple Music の確認済みカタログ ID のみ。別アプリや曖昧な曲検索には使わない。
- 初期の優先順位は Apple 単語 → AMLL 単語 → LRCLIB。Apple 行同期と描画モデル拡張は後続にする。
- 取得不能のフォールバック、既存キャッシュからの格上げ、認証変更時の取り消しを統合テストの中心にする。
- 通信・キャッシュの上限は本書の初期値で明示し、実測値として扱わない。
- 実装を始める前に取得構造の不足を補うTaskを用意し、その後は既存の `codex-run` で順に委譲する。
- Apple IDは正の10進数1〜20桁、入力はUTF-8で16KiBまでとする。storefrontは認証応答から検証して取得する。
- 取得・認証・HTTP・公開Bearerを分離し、新規依存は追加しない。認証世代を観測とキャッシュの鍵に含める。
- 公開初期化は資産各8MiB、JS8本、合計16MiB、30秒。API2MiB、TTML512KiB、曲のApple試行5秒、更新は1回までとする。
- 成功キャッシュは30分・8曲・文字列換算2MiB、取得不可/非対応と一時失敗の再試行抑制は60秒。Retry-Afterがあれば尊重する。
- 利用者による接続確認だけは歌詞オフでも可能にし、歌詞本文を取得しない。自動取得はオフ時ゼロとする。
- 最初の構造診断は未知のキー・URI・属性値を匿名化し、JSON深さ32・異なる経路16個、XML深さ64・要素25,000に制限する。
- 正式版番号、日常利用の認証保持、公開は今回確定せず、ベータ結果を基に決める。
