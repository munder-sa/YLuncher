# AMLL TTML DB 歌詞取得 設計案

- 日付: 2026-11-04。対象版: **次の版**(版番号は未決)。
- 本書は Task 156 の文書成果物。以下の推奨値は実装計画用の提案であり、実機確認済みの値ではない。
- 基準: [既存の歌詞設計](2026-11-03-lyrics-design.md) §3・§3.4・§10〜11、[v2.0 の表示設計](2026-11-04-v2.0-lyrics-visual-design.md)、`tasks/156-research-ttml.md.txt`、Task 156 に記載された Claude の確認結果。

## 1. 目的と範囲

確実に曲を照合でき、主旋律に単語開始時刻がある場合に AMLL TTML DB を使う。優先順位は **AMLL の単語同期 → LRCLIB の同期歌詞 → LRCLIB の平文**。AMLL 未収録・曖昧・非対応・通信失敗は既存 LRCLIB 処理へ進む。LRCLIB 自身の拡張 LRC の単語時刻も引き続き表示する。

背景歌詞(`x-bg`)・翻訳・音訳・歌い手別表示・同時進行する対唱の忠実な再現は範囲外。AMLL の描画コードは取り込まず、既存 `LyricLine`・`LyricWord` と Task 138 の塗りを使う。歌詞本文・実在曲の TTML をアプリやテストに同梱しない。

ユーザーは、DB が CC0 である一方、外来データは元の提供者の条件に従う点を承知して、個人端末での表示に使うと決定済み。README と導入手順に [AMLL TTML DB](https://github.com/amll-dev/amll-ttml-db) と歌詞の作者への感謝を記す。全歌詞が無条件に CC0 と説明しない。本作業では外部照会をしていない。

## 2. 確認済み事項と実装開始の条件

現行コードでは `LyricsQuery` は曲名・歌手・アルバム・秒数のみ。`SessionSnapshot` → `NowPlaying` にサービスの曲 ID は渡らない。`LyricsCache` は v3、Missing は24時間、最大300件。Repository はキャッシュ命中で終了する。再試行は10・30・60秒。旧設計 §3 の v2・7日ではなく §10〜11 とコードを基準にする。

Task 156 の確認結果では全体索引 `metadata/raw-lyrics-index.jsonl` は約1.7MB、am 用は約4.2MB、ncm 用は約5.8MB。metadata の各値は配列。Apple ID `1537460612` の `am-lyrics/1537460612.ttml` は200・約36KB。ただし Apple Music Android の MEDIA_ID がカタログ ID であるかは**未決**。

実装前に Task 157 で人が実機の値を確認する。未確認の数字をカタログ ID として採用しない。併せて、ネットワークを許可された将来 Task で索引の実際のフィールド・改訂・TTML パスの表現、TTML の namespace・時刻・歌い手の構造を確認する。本書は不明なフィールド名や最新履歴の選び方を推測して固定しない。確認資料がなければ該当する reader の実装を止める。

## 3. 照合

### 3.1 識別情報

案Aは確認済み Apple カタログ ID で直接取得、案Bは全曲索引照合のみ。**Aを先に試し、利用できなければBを使う案を推奨**する。直接経路では索引取得が不要になる。

`LyricsQuery` の既存キャッシュ鍵を変えず、別の `LyricsIdentity(appleMusicId: String?, isrc: String?)` を `SessionSnapshot`・`NowPlaying` に既定値付きで追加する案とする。`LyricsRequest(query, identity)` を取得単位にし、Repository の観測鍵に pkg と identity も含める。位置・再生状態・ジャケット更新は取得を起こさない。曲名・歌手が無いときは従来どおり取得しない。

Apple ID は Apple Music の確認済み package/key/形式の組だけ許可する。URL の ID 部分は正の10進数字列のみ。ローカル曲 ID・プレイリスト ID・URL からの推測抽出は行わない。複数キーが矛盾すれば直接経路を使わない。直接404/非対応なら索引を1回検索し、通信障害なら余分な照会を増やさず LRCLIB へ進む。

ISRC の実機供給元も未決。取得できたと確認できる場合だけ使用する。ISRC は大文字化しハイフンを除き、英字2文字・英数字3文字・数字7文字を検証する。未知のキーを総当たりしない。

### 3.2 索引照合の推奨規則

類似度の点数で自動採用する案より、正規化後の一致と一意性を使う案を推奨する。誤曲表示を避けるため、候補ゼロ・複数は不採用。

1. 文字列は NFKC → `Locale.ROOT` の小文字化 → Unicode 空白の連続を半角1個にまとめる → 前後空白除去。記号、アクセント、live/remix/remaster 表記は消さない。
2. 末尾の `(feat. …)` は基礎曲名と参加者を分離して照合する。参加者も正規化一致が必要で、単純に削除して別バージョンへ結び付けない。それ以外の括弧や ft/featuring の展開はしない。
3. 歌手文字列を `/`・`&` などで推測分割しない。入力は索引 `artists` 配列の1要素との完全一致が必要。合成された複数歌手の入力が合わない場合は不採用。
4. 有効な ISRC がある場合はその一致を先に絞る。ただし曲名・歌手が矛盾すれば不採用。ISRC が一致しない場合に文字列だけで別 ISRC の曲へ落とさない。
5. ID/ISRC が無い場合は曲名+歌手一致。入力にアルバムがあるときはアルバム配列とも一致が必要。無いときは曲名+歌手だけで一意の場合のみ採用。
6. 同じ取得先へ至る重複は1候補とする。異なるパス・改訂が残る場合、行順や最大 ID で選ばない。索引仕様で検証した改訂関係がある場合のみ最新へまとめ、それ以外は曖昧として棄却する。

索引は音源長を持つと確認できていないため、長さの近さによる順位付けはしない。TTML の主旋律開始が既知の曲長を超える場合は非対応として棄却する。サービス間の音源差によるずれは残るため、ベータ実機で確認する。

## 4. 索引の取得・検索・資源上限(推奨値)

全体索引を推奨する。am 用より小さく他サービスの情報も利用できる。取得元は `https://raw.githubusercontent.com/amll-dev/amll-ttml-db/main/metadata/raw-lyrics-index.jsonl` のみ。自動ミラー切替は今回行わない。

- 歌詞オンで索引が必要になった時だけ更新。成功・失敗を含む更新試行は24時間に1回まで。同時要求は1本にまとめる。バックグラウンド定期通信は作らない。
- `files/lyrics/amll-index/` に正規化済み JSONL 表と更新管理情報を置く。元の全 JSON 木や全索引を常駐させない。IO で1行ずつ読み、保持するのは現在曲の候補だけ。複数の相異なる候補を見つけたら曖昧判定に必要な情報だけ保持する。
- 表の各行は正規化曲名・歌手配列・アルバム配列・ISRC 配列・確認済みの取得先/改訂識別子。フィールドの実際の対応は Task 157 の資料に基づき確定する。
- 索引の受信上限8MiB、行上限64KiB、生成表上限8MiB。一時元ファイル8MiB・一時表8MiB・旧表8MiB のピーク24MiBと小さな管理情報を見込む。成功後は表1個だけ残し、元索引を保存しない。上限ちょうどは可、1byte超は中止。
- 不正 JSON、必須フィールド欠落、途中切断、上限超過では更新全体を失敗にする。検証済み一時表を同じディレクトリで置き換え、途中の表を公開しない。起動時に未完成の一時ファイルを除去する。
- 更新失敗時は最後の正常表を使い続ける。古い表で未収録でも永続的な結論にしない。次回更新可能時に再判定する。正常表無しなら LRCLIB へ。
- 304/ETag 対応は将来拡張。今回は有界な1日1回の GET を推奨する。既存文字列応答の `HttpTransport` で索引全体をメモリに載せず、AMLL 専用ストリーム transport を追加する。

TTML は検証済み ID の `am-lyrics/<id>.ttml` を優先し、索引検索時は確認済みの対応パスを使う。取得先は固定 HTTPS ホストと確認済みフォルダー+安全な ID のみ。索引の任意 URL を直接開かない。

TTML と LRCLIB の上限は各512KiBのまま。索引だけ8MiB。接続/読み取り5秒、redirect を追わず、既存 User-Agent を使う。通信・ディスク・XML解析は IO、検索正規化もメインで行わない。キャンセル時に stream を閉じ disconnect し、キャンセル例外を再送出する。

## 5. TTML の変換(推奨する対応範囲)

Android 標準 `XmlPullParser` を namespace 有効で使う。外部実体・DTD を受け付けず、DOCTYPE は棄却。外部リソースを解決しない。深さ64まで、1曲2,000行まで、1行16,384 UTF-16 code unitまで、1曲20,000単語開始までを追加上限とする。超過や XML 破損は全体を棄却し LRCLIB へ進む。

- `<p begin>` を `LyricLine.timeMs`、主旋律の時刻付き `<span begin>` を `LyricWord.timeMs` に写す。時刻は非負の `hh:mm:ss[.fff]` と `数字[.小数]s` を対応案とし、小数1〜3桁をmsへ補い、秒・分は0〜59、加算オーバーフローは棄却する。相対時刻、フレーム/tick、未対応の時間コンテナーを推測変換しない。実データ確認で別形式が必要なら仕様と試験を先に更新する。
- namespace prefix の文字列に依存せず URI/local name で読む。通常の agent 属性は捨てて主旋律行を時刻順に並べる。複数歌い手の識別は保存しない。主旋律行の時間区間が重なる対唱は不採用とし、複数行を同時に表示する変更はしない。
- `x-bg`・翻訳・音訳の subtree を本文と文字位置の計算から除外する。これらの具体的な属性/namespace の検出は Task 157 の資料で確定し、未知の意味付き拡張は主旋律と推定せず非対応にする。
- 本文は主旋律のテキストノードを文書順で連結し、XML 実体を復号する。span 間に勝手な空白を足さない。字下げだけの改行ノードは捨てるが、同一行の明示的な空白は保持。`xml:space="preserve"` は保持する。前後を trim して charStart をずらさない。
- `charStart` は連結直前の Kotlin `String.length`(UTF-16)。例: `あ😀` の次の単語は3。時刻の無い主旋律の装飾 span は本文に含める。時刻付き span の入れ子は重複した単語を作らず非対応とする。
- 行は開始時刻で安定ソート。同時刻の主旋律行や、単語開始の逆転・重複・行開始以前・既知の次行開始以降は不採用。時刻を並べ直して文字位置との対応を壊さない。空行は捨てる。主旋律が無い/単語時刻が1つも無い曲は AMLL 採用不可。
- `end` は、あれば start より後か・単語が行区間内か・主旋律が重ならないかの検証だけに使う。モデルには保存しない。無ければ次行開始を区間の上限として扱う。最後の行で区間を確定できない場合は重なりなしの単一行だけ許可する。
- 表示は既存の「次の単語開始まで補間、最後の単語は次行/曲長/既存5秒終端」を使う。TTML の end と休符は忠実に再現しない。単語時刻の無い行は行全体強調にし、推測の塗りは足さない。

## 6. ソース別キャッシュと失敗

案Aは既存キャッシュを v4 にして全取得し直す案。案Bは既存 v3 を LRCLIB 専用として残し AMLL を別に保存する案。**Bを推奨**する。既存の取得済み LRCLIB を失わず、AMLL を先に確認できる。

`files/lyrics/` の v3・300件は LRCLIB 専用のまま。Repository の無条件早期 return を改め、AMLL キャッシュ/照合/取得を先に評価する。AMLL が採用できなければ LRCLIB キャッシュ、無ければ既存 client を呼ぶ。LRCLIB キャッシュ命中でも AMLL の確認を省略しない。

AMLL は `files/lyrics/amll/` に v1 のエントリーを保存。鍵は正規化前の既存 query.cacheKey と検証済み identity を JSON 配列化して SHA-256。ソース名・取得先・索引世代・savedAt・変換済み lines/words を記録し、生 TTML は保存しない。曲ごとに1回取得して利用し、改訂の追従は今回は手動キャッシュ削除後とする。成功キャッシュは期限なし。ただし parser 仕様を変える場合は AMLL 形式版を上げる。

AMLL は最大300件・合計32MiB・1ファイル1MiB。書き込み時に古い savedAt 順で削除、超大の結果は表示だけして保存しない。索引とは別枠。成功・負の記録を合わせて上限に数える。原子的な一時書き込みを行い、ディスク失敗は表示を妨げない。

404、正常索引で候補なし/曖昧、正常TTMLだが単語なし/非対応はAMLL側の負の記録として24時間。索引世代または identity の変化で早期無効化する。通信障害・429/5xx・壊れたXML/JSON・サイズ超過は Missing として保存しない。索引取得失敗を「曲が無い」と保存しない。LRCLIB の Missing は従来どおり24時間で別管理する。

AMLL の障害でも LRCLIB の表示可能な結果を採る。両方表示不可のときは、AMLL に一時障害があれば LRCLIB Missing より Offline/Failed を優先し、既存の10・30・60秒の再試行対象にする。LRCLIB の `cacheable=false` は守り、ソースごとの結果を独立に保存する。

AMLL の同一要求の即時 retry はしない。429/503 の Retry-After の正の秒数、無効なら60秒を AMLL ホスト全体の待機に使い、それ以外の一時失敗も同一曲は最低60秒空ける。LRCLIB の全体待機とは分離し、AMLL 待機中は LRCLIB へ進む。LRCLIB が成功した後に AMLL の再取得だけを目的としたタイマーは作らない。次の曲変更/オン時に期限を再評価する。

## 7. 表示・通信・性能

取得元ラベルを小さく追加する案と、説明文だけに表示する案を比較し、**今回は README/導入手順のみ**を推奨する。歌詞の場所や文字寸法・MediaCard の1行・semantics を変えない。取得元はキャッシュと本文を含まない診断で追えるようにする。

オフ時は索引・TTML・LRCLIB とも要求を開始せず、進行中の取得も取り消す。600ms debounce、世代管理、曲変更/消失時のキャンセルを維持。ブロッキング読み取り終了後も有効世代を確認してから表示・保存する。

コールド時の最大通信は索引8MiBを1日1回、照合した TTML 512KiBを曲ごとに1回と既存 LRCLIB。キャッシュがあれば繰り返し TTML を取得しない。GitHub に曲名検索クエリは送らず照合は端末内。GitHub には IP と索引/照合済み曲 ID の要求が送られ、LRCLIB には従来の曲情報が送られる点を導入手順に書く。

v1.7.1/v2.0 の層による移動・フェード・縮小、静止背景の共用、可視行制御を維持。毎フレームの再組立て・再計測・再配置を増やさない。単語同期/間奏以外に常時フレーム処理を足さない。リリース画面の「パネル」1ノードを維持する。

## 実機・データの確認(Task 157 Step 3・4、2026-11-04、Claude)
- **MEDIA_ID は Apple Music のカタログの曲 ID**(確定)。`android.media.metadata.MEDIA_ID` と `com.apple.android.music.playback.metadata.METADATA_KEY_MEDIA_ID` は同じ値の文字列(Apple Music for Android、GT8D)。例: 夜の踊り子=604748203、なんてったって春=604748204。iTunes Lookup(`https://itunes.apple.com/lookup?id=<id>&country=jp`)で曲名・アーティスト・アルバムが一致。曲送り・戻しで値が変わる。
- よって Apple Music の再生では `am-lyrics/<MEDIA_ID>.ttml` を直接取る経路を採る(索引の照合より優先)。404 は「未収録」(夜の踊り子 604748203 は 404)。Lemon の 1537460612 は 200。
- ISRC は metadata に無い(採らない)。
- **TTML の形**(Lemon で確認。本文は載せない): ルート `<tt xmlns="http://www.w3.org/ns/ttml" xmlns:amll="http://www.example.com/ns/amll" xmlns:itunes="http://music.apple.com/lyric-ttml-internal" xmlns:ttm="http://www.w3.org/ns/ttml#metadata" itunes:timing="Word">`。`head/metadata` に `ttm:agent` と `amll:meta key=… value=…`(musicName・artists・album・appleMusicId・isrc・ncmMusicId・qqMusicId・spotifyId・ttmlAuthorGithub・ttmlAuthorGithubLogin)。`body/div/p begin end itunes:key ttm:agent` の中に `span begin end`(単語)。時刻は秒の小数(例 `1.372`)。`span ttm:role="x-translation"`・`"x-roman"` は翻訳・ローマ字(捨てる)。背景の歌詞(`x-bg`)はこの例には無いが、あれば捨てる。
- 時刻の形は秒の小数のほか、`mm:ss.mmm` などもありうるので、読み取りは両方を受け付ける。不正な時刻・単語の順の矛盾などがあれば、§5 どおり **TTML 全体を棄却**し(Invalid)、LRCLIB へ回す(一部の行だけを使わない)。
- (2026-11-04 司令塔)§6 の「索引の世代が変わったら負のキャッシュを無効化」は v2.1.0 では**延期**。未収録の記録は 24 時間で切れるので、索引の更新の反映が最大 1 日遅れる。
