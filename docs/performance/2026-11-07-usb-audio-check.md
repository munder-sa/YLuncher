# USB の adb での性能検証と音飛びの確認 (2026-11-07)

- 担当: Claude(司令塔)。実機は 2.3.2 / 56。接続は USB の adb(`-s 12345678`)で、ワイヤレスの adb の通信は使っていない。scrcpy は終了済み。
- 再生は Apple Music(サカナクション、ロスレス表示)。音声の出力は `AudioOut_15`(SPEAKER、48kHz、HAL 1920 フレーム)。Apple Music のトラックのバッファは 14,144 フレーム(44.1kHz で約 320ms)。
- 計測は Claude の一時スクリプトで行った(リポジトリには入れていない)。5 秒おきに `dumpsys media.audio_flinger`、`/proc/*/stat`、主要プロセスのスレッドの stat、CPU の周波数、温度を読み、logcat も取った。端末の設定は変えていない。

## 結果

| 場面 | 時間 | 書き込みの遅れ | ミキサーの underrun (partial/empty) | トラックの underrun | 全 CPU(8 コア平均) | 主な CPU(1 コア = 100%) |
|---|---|---|---|---|---|---|
| A: ホームで歌詞を表示 | 120 秒 | 0 | 0/0 | 0 | 16.2% | Apple Music 22.8、ランチャー 7.2(RenderThread 3.7)、audioserver 6.2、surfaceflinger 4.1 |
| B: セット 2(Apple Music + マップの分割) | 120 秒 | 0 | 0/0 | 0 | 20.4% | Apple Music 39.4(最大 94.6)、マップ 10.3(最大 81)、YouTube 8.5(最大 89) |
| C: ホーム・セット 4・セット 2・アプリ一覧を 4 秒おきに切り替え | 120 秒 | 0 | 0/0 | 0 | 24.5% | Apple Music 24.8、マップ 19.8、system_server 15.3(最大 39.5)、ランチャー 4.1 |
| D: 8 コアに `yes` で負荷をかける(ホーム) | 60 秒(+計測なしで約 3 分) | 0 | 0/0 | 0 | 100% | — |

- **端末の中(アプリ → AudioFlinger → HAL)では、音飛びは 1 度も起きていない。** 8 コアを使い切っても、underrun は 0 だった。音声のスレッドの優先度とバッファで、CPU の負荷には十分に耐えている。
- 書き込みの遅延の最大は約 149ms。HAL の周期(1920 フレーム = 40ms)を何回か溜めて書く方式で、平均は 147ms で安定している。
- 負荷をかけ続けた約 4 分で、CPU の温度は最大 93.5℃ に上がった。周波数の上限(2.07GHz)は下がらなかった。
- YouTube(使っていない、キャッシュ状態 oom 900)が、裏で 1 コアの 89〜93% を使う瞬間がある。切り替え中には `Davey! 730ms` が出た。
- Apple Music の LOW_MEMORY による終了は、記録上すべて、裏で止まっていたとき(importance 400 / empty)のもので、再生中ではない。

## 範囲外・未確認

- **車での音の経路は今回測っていない。** USB のカーモードでは、suding の投影サービス(`sdCarplaySvc` など)が音を車載機へ送る。この区間の途切れは、USB の adb のモードでは再現できない。
- **ネットワークによる途切れは測っていない。** 再生はロスレスで、車ではスマホのテザリングを使う。電波が弱いところでの再生待ち(BUFFERING)は、Wi‑Fi が安定している室内では起きない。
- そのため、車で音飛びがあれば、原因の候補は (1) 通信(ロスレスの容量と電波)、(2) 車載機へ送る区間、の順に考える。端末の CPU の負荷は候補から外してよい。
